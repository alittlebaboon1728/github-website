## 1. 先理解项目与本轮目标

先读 README.md、DESIGN.md、PROGRESS.md、docs/COMPETITORS.md，并查看 docs/screenshots/ 下的当前界面截图，再阅读实际生效的组件和样式。

网站帮助用户发现 GitHub 公开项目、理解用途、判断是否适合自己，并找到开始使用的入口。这轮要形成连贯路径：

**说出需求 → 获得相关项目推荐 → 阅读优点与限制 → 了解近期动态和趋势 → 阅读相关博客 → 收藏或开始使用。**

必须覆盖五项能力：参考 Console.dev 的编辑评价、参考 OSSInsight 的「GitHub 现在发生了什么」、博客汇总、排行榜与热门趋势、能理解自然语言并支持追问的项目搜索。

用户已结束竞品扩展，重点参考以下三个产品，不必继续扩大竞品清单：

- Console.dev：https://console.dev/tools —— 学习明确说明优点、限制和取舍的评价方式。
- OSSInsight：https://ossinsight.io/ —— 学习近期 GitHub 活动的观察方式、数据组织与趋势探索。
- HelloGitHub：https://hellogithub.com/ —— 学习具体自然的中文项目说明、真实预览和内容筛选。

理解它们解决的问题，并融入本站；保留原创布局与表达。

## 2. 延续当前 UI，重新组织信息层级

沿用当前暖白、简洁、内容优先的视觉：背景 #fafaf7、正文 #252923、次级文字 #62665e、操作色 #333d30、来源强调 #bb4a30，淡紫用于少量专题和示例。复用已有字体与语义色，深色主题单独适配。

保持顶部导航、左对齐、清楚的文字层级、能说明内容的预览、轻量边框和克制的动效。项目卡片与快速阅读继续承担主要浏览任务。卡片动效要保留，手机上无需 hover 也能完成操作。

这次需要调整布局与信息组织，不能只改颜色和阴影。新增功能应看起来属于同一个网站，避免为每个模块创建一套视觉。

- 主导航控制在约五个入口：发现项目、趋势与榜单、博客、项目试用、我的收藏。自然语言搜索贯穿首页和顶栏快捷搜索。
- 首页顺序建议：简短标题与需求搜索 → GitHub 近期动态 → 精选/发现项目 → 热门趋势摘要 → 博客精选。内容较长时通过明确的「查看全部」进入独立页面。
- 近期动态应在桌面首屏或紧接首屏出现；既有 Excalidraw 示例保留，可缩为精选入口或移至发现内容区，不再独占首页的大面积空间。
- 桌面项目仍以两列为主；动态和榜单可使用紧凑行，博客使用文章列表，不把所有内容都塞成相同卡片。
- 手机自然单列，筛选可收起，快速阅读适配全屏；避免横向溢出和依赖鼠标的交互。
- 不增加巨幅宣传区、抽象装饰插画、无含义的数据大屏、持续闪烁的实时标记或遮挡内容的聊天浮窗。

先给出简短的信息架构、桌面/手机线框和视觉继承方案，核对是否满足上述要求，然后继续实现。

## 3. 自然语言找项目是核心入口

用户可以像向懂开源项目的人提问一样输入需求，例如：

- 「推荐几个适合个人用的开源笔记工具，能离线，最好支持中文。」
- 「我想做一个类似 Notion 的知识库，能自己部署，有哪些选择？」
- 「有没有可以在普通电脑上跑的 PDF 问答项目？」

统一搜索框支持自然语言、项目名、owner/repo、GitHub 链接与 GitHub 搜索语法。需要时提供清楚的搜索模式切换或纠正入口，不能让用户猜本次搜索采用了什么方式。保留现有精确搜索与仓库直达能力。

自然语言结果页应提供：

1. 一小段需求理解，以及可编辑的条件标签，区分必须满足与偏好，例如离线、自托管、中文、平台、硬件和技术栈。
2. 一组与需求相关的真实项目；目标约 5–8 个，证据不足时少给，不能为凑数量编造或填入无关热门项目。
3. 每个项目的中文用途、推荐理由、满足哪些条件、有哪些限制和未知项、仓库/官网/文档入口，以及可核实的项目数据和来源时间。
4. 简明的选择建议，例如哪个更易开始、哪个更灵活；相关建议应有来源支持，不输出无依据的匹配百分比或能力承诺。
5. 支持继续追问：「只看 Windows」「不想自己部署」「这些哪个更容易上手」「再找几个更轻量的」。保留原有条件，并正确更新用户修改的条件。

搜索结果复用现有卡片、快速阅读和收藏，让用户能连贯浏览；AI 说明以简短导读和推荐理由为主，避免长篇聊天挤压项目结果。加载时显示真实进行中的状态；支持取消过时请求、重试、无结果建议及浏览器返回恢复条件和位置。普通关键词可提供轻量建议，昂贵的 AI 检索应由用户明确提交触发。

实现真实的检索与推荐链路：需求解析 → 基于真实数据检索候选仓库 → 读取候选资料/README → 按条件排序 → 生成有依据的推荐。不能只让模型凭记忆列项目，也不能把中文关键词替换称为完整自然语言理解。

GitHub 搜索不保证中文语义和 README 全文覆盖；应针对需求生成多组合理查询，合并去重后验证。硬性条件不满足的项目不要混进主推荐；无法确认的能力明确说明，不把缺少说明直接判为不支持。

AI 服务在服务端接入，模型与服务商可配置，密钥不得进入浏览器。若当前没有模型凭据，完整实现可接入的服务边界和错误状态，页面明确说明 AI 搜索尚未配置，并提供普通 GitHub 搜索；演示模式必须独立标识。不能用固定响应冒充已经接通。

## 4. 首页「GitHub 现在发生了什么」

参考 OSSInsight，把开源活动变成用户能看懂、能点开的近期动态组件。

- 使用简洁事件流，可包含公开仓库的新版本、合并 PR、新建仓库或其他数据源实际提供的公开活动。根据所选 API 的真实字段与事件类型实现，不凭设想补出缺失事件。
- 每条动态显示时间、类型、owner/repo、简短中文说明及原始事件/发布页链接；有资料时再补充项目用途。
- 支持暂停/恢复更新、手动刷新、筛选；默认低频更新，切到后台时减少请求。新内容先提示「有新动态」，由用户载入，避免阅读中的列表跳动。
- 桌面可使用紧凑事件列表配一个项目概览或来源说明；手机保留主要事件信息。需要查看项目时复用快速阅读。
- 清楚标明覆盖范围，例如「GitHub 公开事件样本」或「本站关注仓库的近期发布」，显示更新时间。事件时间与抓取时间应区别处理；延迟数据称为「近期动态」，不承诺全站实时全量。
- 不生成假事件、虚构用户名、伪造事件时间或全球滚动计数。没有数据时提供合理空状态、重试或明确标注日期的缓存。

注意：此前调研时 OSSInsight 官网已提示部分基于 stars 等事件计数的排名暂停，不能默认其所有趋势数据当前可靠或可直接复用。选择可持续的数据源，并说明实际覆盖与限制。

## 5. 编辑评价：学习 Console.dev 的判断方式

这轮的「评价系统」首先是结构化编辑评价，不默认增加用户打分、社区评论、账号或声誉系统。

项目详情与快速阅读增加以下内容：

- 适合谁、解决什么具体问题。
- 值得用的地方：约 2–4 条，描述具体能力及其价值。
- 使用前要知道：部署成本、平台限制、功能边界、学习门槛等，有依据才写。
- 不适合什么场景，以及清楚的开始入口。
- 评价日期、依据来源、适用版本（可确定时）和核实方式。

区分「依据文档整理」「实际体验」「AI 辅助整理」，未实际测试就不能写成亲测。缺少资料时显示尚未评价，不能套用通用优缺点凑齐内容。提供少量真实、完整的评价案例，其余项目保持可靠回退。

当前作者视角 README 中文转述可以保留，但必须与本站编辑评价明确区分：转述继续标明非作者原话；评价使用本站视角，避免用项目作者口吻自我评价。AI 推荐理由同样单独标识。卡片只露出最有用的一条判断，完整内容放在快速阅读与详情。

## 6. 博客汇总

建立可浏览的开源博客聚合页，首页展示少量精选。来源优先采用公开、可核实的官方博客与 RSS/Atom，配合人工精选，涵盖项目发布、实用教程、技术实践与编辑评测。

- 每篇展示原始标题、来源、作者（可获取时）、发布日期、语言、主题和短摘要；中文摘要明确标注整理性质。
- 支持主题、来源、语言与日期筛选，搜索、分页/加载更多，并按规范链接去重。
- 展示关联的开源项目，从文章进入项目快速阅读，从项目详情找到相关文章，形成真实关联。
- 默认跳转原文；注明来源，避免整篇复制外部文章。没有封面时使用清楚的文字排版，不用随机图片填充。
- 来源配置、抓取与缓存放在服务端；单一来源失败不拖垮其他来源，显示上次成功更新与缓存状态。初期只做足够验证体验的小规模可靠来源。

## 7. 分清排行榜与热门趋势

在同一「趋势与榜单」页面中提供两个清楚的视图：首页只露出摘要。

- 排行榜回答「在这个范围内，谁排在前面」：可实现总 stars、限定创建时间的新项目榜等，并显示排名、指标、数据时间与查询范围。
- 热门趋势回答「最近一段时间，哪些项目关注度上升」：有可靠历史数据后再提供日/周/月 stars 净变化及趋势线，明确时间窗口、计算方式和覆盖的仓库集合。
- 总 stars、最近推送时间、创建日期都不能冒充近期关注增长。不要把近期创建项目榜写成近期新增 stars 榜；不把净变化称为新增关注人数。
- 若需要历史数据，从真实采集开始持久化快照；历史不足时只显示已有窗口，说明「正在积累数据」，不能补造历史曲线。未配置持久化时明确不可用，不能依靠进程内数据承诺跨日榜单。
- 排名变化只有相同范围、相同算法的可比快照存在时才显示。GitHub 搜索结果上限与索引延迟也要纳入范围说明。
- 按用途、语言、时间等有效维度筛选，点击项目进入已有详情/快速阅读，支持收藏。只有数据充分的筛选组合才开放，缺少历史时明确解释。

## 8. 实现范围与质量要求

沿用 React 19、TypeScript、Vite、现有 Node HTTP 服务、Lucide、React Markdown 和已有 Excalidraw 集成。扩展现有工程，按职责拆分模块，避免将全部逻辑继续堆入首页组件。

优先核对这些入口：src/ExplorerApp.tsx、src/discovery.css、src/explorer.css、src/components/RepositoryCard.tsx、QuickRead.tsx、ProjectIntroduction.tsx、DiscoveryShelf.tsx、src/projectGuides.ts、src/useReadme.ts、server/github.mjs、server/index.mjs。src/main.tsx 当前使用 explorer.css 与 discovery.css；旧样式文件不代表当前有效方案。

保留真实仓库搜索、README 安全渲染、错误/限流提示、缓存、收藏与主题持久化、卡片/列表切换、快捷搜索、快速阅读焦点与位置恢复，以及 Excalidraw 编辑、保存和 SVG 导出。暂不扩展新的完整动态图解案例。

新增数据请求要有服务端缓存、并发合并、超时与限流处理；历史趋势/内容采集采用适合当前部署的持久化方案，清楚说明本地与生产的差别。首次访问不应等待所有博客源、README 和 AI 响应全部完成。根据需要分批和按需加载。

真实、缓存、演示数据的状态要可识别；涉及质量判断的内容保留来源与时间。正常浏览尽量无需账号。不要为实现本轮目标额外扩展社交、付费和复杂个人中心。

按钮、导航、筛选、追问和刷新均需真实反馈；覆盖加载、空结果、失败、离线、限流、服务未配置与历史不足状态。保证键盘可用、焦点可见、触控区域合理、文字对比充分，并尊重减少动画偏好。

## 9. 执行与验收

先审阅现有界面，简短说明页面结构和数据方案，再分模块完成实现。常规实现选择自行判断并继续推进；缺少凭据时完成其余工作，清楚列出该能力的接入条件与当前状态。

完成前验证：

1. 自然语言推荐有真实项目和证据，追问能正确继承/修改条件，普通搜索仍可用；未接入模型时诚实降级。
2. 动态流可追溯原始链接，刷新与暂停有效，不扰乱阅读位置。
3. 编辑评价包含真实优点与限制，来源、日期与身份清楚。
4. 博客可筛选、去重、关联项目并打开原文；单源失败可恢复。
5. 榜单与趋势指标准确，缺失历史时不出现假增长或假曲线。
6. 收藏、快速阅读、README、主题与 Excalidraw 的已有能力没有回归。
7. 检查约 360/390、768、1024、1440px 的浅色与深色页面，查看实际截图，确认无横向溢出。

根据改动扩展必要的行为测试；AI、博客源与 GitHub 可用确定性数据验证逻辑，另做条件允许的真实接口冒烟，不将 mock 通过写成线上服务已核实。运行 npm run build、npm run test:server、npm test，修复引入的问题。

最后提供：可运行成果、关键页面截图、验证结果、数据与模型配置方法，以及已完成/待外部配置的明确清单；更新 README.md、DESIGN.md、PROGRESS.md。不要仅交付静态概念图、空入口或只有计划的答复。
